# 43. SVG sprites

**Status:** built (`games/spaceinvaders2.xml`, `tests/test_svg_sprites.cpp`); new tag: `<svg>` (with `<path>`, `<x>`, `<y>`, `<width>`, `<height>`, `<scale>`, `<hide>`); new library: lunasvg, used only by `lib/source/svg.cpp`

## Why

A sheet of sprites drawn in a vector editor (the Space Invaders sheet: six frames across, four rows, 32 units a cell) cannot be used today. `<bitmap>` is text, and `<image>` hands the file to whichever window backend is running, which cannot be relied on to read an SVG: SDL2 and OpenGL go through SDL_image, which can, and SFML and raylib (as built here) cannot. The pictures that came out would also differ from library to library, and a `pixel` collision could not test them, since a backend's pixels are only known to the backend (the limit noted at the end of [42](42-bitmap-sprites-and-animation.md) and in the readme).

## The language

`<svg>` is one more shape, beside `<bitmap>`: where a sprite can hold a `<bitmap>`, it can hold an `<svg>`, a `<grid>` can repeat it and an `<animation>` can use it as a frame. `<path>` is the file. `<x>`, `<y>`, `<width>` and `<height>` take a part of the drawing, in its own units; `<scale>` is pixels to a unit (it can be 1.5); each `<hide>` names the id of an element to leave out.

## Decisions

- **The engine draws it, once, when the game loads, into the same `Bitmap` a `<line>` or `<bitmap>` sprite makes.** This is the answer to "how do all the backends show an SVG": none of them is asked to. It is the same decision made for lines and ASCII sprites, and it means no window backend, the Qt renderer or the collision detector changed. The shape kind is still the internal `Line` ("a picture the engine drew itself"), the params are still `{"line", w, h}`, a grid's cells share the one picture, and a turning object keeps it as a `Turnable` picture.
- **Not exposed as a backend.** It has no interface, factory, command line choice or Options entry: there is one way to draw an SVG and a choice of libraries would only add ways for the same sprite to look different. `svg.h` speaks only in the engine's own `Bitmap`, `svg.cpp` is the only file that includes the library, and the library is linked `PRIVATE` to `XGELIB`, so nothing that includes the engine's headers needs it.
- **lunasvg, v3.5.0.** The requirements were small, easy to build from source on every platform the project builds on, no dependency on a window or graphics library, a permissive licence, and enough of SVG to draw the sheet. The sheet defines the ship once in `<defs>` and shows it three times with `<use>`, with rotations, strokes, rounded rectangles, ellipses and opacity. lunasvg does all of that (and brings plutovg, its own small 2D rasterizer, inside it, so nothing else is fetched); nanosvg, the smaller choice, does not support `<use>`. It is built from source by `FetchContent` like the other libraries (`FORCE_LOCAL_LUNASVG` forces that), or found through `find_package(lunasvg)` (for example from vcpkg; that path was not tried). It is fetched pinned to the tag with its examples switched off. It writes no `stb_image` symbols of its own, so it does not add to the duplicate symbol problem of fetching both SFML and raylib (see the agent notes).
- **A part of a drawing, not one file a sprite.** The sheet is one file with every picture in it, so each sprite takes its cell by `<x>`, `<y>`, `<width>` and `<height>` (all four or none, so a typo cannot silently mean the whole sheet). The drawing is loaded once for each sprite, which costs little for a 16 KB sheet. A cache by file would be easy to add if it ever does not.
- **The part is cut close round what is drawn, on purpose.** A cell of 32 units has a margin of empty space round every picture, and the box used for non-`pixel` collisions is the whole picture. The Space Invaders 2 sprites are cut to the drawn pixels (all three frames of one alien share one cut, since an animation needs the frames the same size, and the cut is centred so the columns line up). `type pixel` would tighten it further, but a cut this close is already about the size of what is drawn, and it keeps the aliens on the plain box test they had.
- **`<hide>` by id, not a second copy of the file.** The sheet has a dark backdrop with a grid ("delete this group for a transparent PNG"). The file stays as its author drew it, so it still looks right in an editor, and the game says what to leave out. The id goes into a one-line style rule (`#id{display:none}`) that lunasvg applies, so it only takes plain ids (letters, digits and `_ - . :`) and refuses anything else. A drawing that has no group of that name is not an error: a sheet with its backdrop already removed works with the same game file.
- **Colors are the drawing's own.** There is no `<color>`, since one color per picture was the limit of `<bitmap>` and is the reason to want an SVG. Pixels are straight (not premultiplied) RGBA, as the backends expect, and the edges are antialiased partly transparent pixels.
- **Fractional scale, whole pixels.** A cut 28 by 24.5 units at a scale of 2 is 56 by 49 pixels: the size is rounded up, never down, so no edge is lost.
- **A pixel collision treats any pixel with alpha above 0 as solid.** That is what `Bitmap::solidAt` means for every picture, and a faint antialiased edge counts. A threshold would be a change to the meaning of "solid" for all sprites, so it was left.
- **Mistakes stop the load**, naming the object and the file, like every other sprite mistake: a file that is missing or not an SVG, a scale of 0 or less, a part with only some of its four numbers or no size or none of it inside the drawing, an id that is not an id.

## Space Invaders 2

`games/spaceinvaders2.xml` is `spaceinvaders.xml` with the pictures replaced, as a second game so the ASCII one stays as a reference. The structure is the same: one group of three members, each a grid of its own sprites that march, bounce and step down together. What changed:

- The three kinds of alien are rows 2 and 3 of the sheet (pink squids from the first three cells of row 2, orange crabs from the last three, green octopuses from the first three of row 3), each with **three** frames and an `<animation>` of three `<frame>`s, a half second apart (the first version was two frames a second apart).
- The ship is the idle ship, cell (0, 0), and the bullet is the player bolt, cell (4, 0), at a scale of 1.5. Both are cut close.
- The aliens are all 56 pixels wide (28 units at a scale of 2), so a column is 56 plus the gap of 15 wide for all three kinds, and the rows are different heights (50, 46 and 49 pixels), which the formulas for each member's `y` already allow for.
- The rest of the sheet is unused for now: **banking left and right, the hit flash, the charged bolt, the enemy bolt and bomb, the four explosion frames and the saucer.** All of them are in the language in the sense that an `<svg>` can cut them out; what is missing is something to show them with. The ship's banking is a picture that depends on which key is held, the hit flash and the explosions on a collision or a death (an explosion also wants an object to appear where an alien was, and an alien that dies today is just not shown), the enemy bolts on aliens firing, and the saucer on an object that crosses the top now and then. Those are the same limit [42](42-bitmap-sprites-and-animation.md) names ("a picture that depends on something other than time"), and are the next natural step.

## Options considered

- **nanosvg**: smaller, one header, but no `<use>`; the sheet's ship would have to be written out three times. Rejected for the sheet it was asked to load.
- **Let SDL_image load it** (it can): works for two of four backends, and the pictures would differ from the other two and from the pixels a collision tests. It would also make the choice of backend change what a game looks like.
- **Convert the SVG to a PNG in the build.** Works with every backend and needs a tool at build time and a second file in the repo to keep in step; it could not take a part or a scale from the game file.
- **Rasterize at the size the window is drawn at** (resolution independent sprites). The engine's units are pixels and `<scale>` already says what a unit is; redrawing on a resize is a bigger change and not needed.
- **A palette or recolor** for sprites that differ only by color. The sheet already has them in different colors.
- **Caching the loaded drawing by file name.** Cheap to add if loading the same sheet for every sprite ever shows up as slow.

## Later: flipping, and one path for every drawn picture

On 2026-10-03 `<flip>` (horizontal or vertical) was added to `<svg>` and `<bitmap>` sprites, applied to the pixels right after the picture is drawn and before it is kept for turning, so a flipped picture keeps its exact size and a pixel collision tests the flipped pixels. Turning a picture half a round with a `<heading>` would have done the same for a vertical flip, but every heading's picture is one square big enough for any angle, which would have given Space Invaders 2's thin falling bolt (the sheet's enemy bolt, drawn flying up, now `<flip>vertical</flip>`) a box about 38 pixels square. The code that draws lines, bitmaps and SVGs was made one path (`game_expr::buildSpriteParams`): read, draw, flip, keep for turning. Lines still turn by drawing the turned lines again, not by turning their pixels, which keeps them sharp. Tests: `tests/test_pictures.cpp`.
