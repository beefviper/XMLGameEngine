# States and conditions

**Status:** Built. Per-state object behavior, object-level conditions and passing data between states are open.

## States

- A `<state>` is a **screen**: menu, playfield, pause, game over. It says what is shown, which keys run which commands, which conditions to watch, and its own timers. A state is a template; which one is current is runtime.
- **Chosen: a stack.** `<push>` / `<pop>`; pause is space in `playing` pushing `paused` and space in `paused` popping. A bare `<reset />` from a state input or condition collapses the stack to the first state, so menu → play → game over → menu does not grow. The first state is never popped. The state stack holds copies, so state timers live in `Game::stateTimers` by name.
- **Moving on without growing the stack (2026-10-07): `<pop state="wave2" />`.** Kaboom's waves and Berserk's rooms used to `<push>` the next, so the stack grew by one each time until a reset. Looked at: a `<goto state>` verb; `<reset to="...">` or `<reset>wave2</reset>` (the author's first ideas); and an attribute on `<pop>`. Chosen: `<pop state="...">`, "this state goes, and that one takes its place": no new verb, the attribute picks the state as `push`'s does, and it reads as what happens. It replaces the first state too rather than leaving the stack empty. Kaboom and Berserk used it until their waves and rooms became [scenes](12-scenes.md) (2026-10-15), moved on by `<enter scene>`.
- **Show sets (built 2026-10-13): `<shows name>` beside `<keys>`.** Pitfall's four screens listed the same nine objects each; Berserk's rooms, the waves of Kaboom, Missile Command, Megamania and Demon Attack, and Asteroids' and Lunar Lander's play and end screens the same. Counted before: 191 `<show>` lines repeated an object another state of the game already showed. A named `<shows>` set at the top of `<states>` holds `<show>`s; a state takes it with `<show set="name" />`, one set to a `<show>`, and lists what it adds. A set can take a set written before it (Berserk's `room` takes `hud`, which the pause and game-over screens take too). The reader expands a set in place, so `RawState::show` and everything after it are unchanged; the generator expands it the same way. Eight games went 13,561 lines to 13,497. Since 2026-10-15 states own their objects and places are [scenes](12-scenes.md), so most of those sets went away again; Air-Sea Battle's `end` is the one left.
  - Why one set per `<show>` and not `<shows sets="a b">` as `<inputs keys="a b">` is: a list of names packed in one attribute is data hidden in a string ([file-format](02-file-format.md)).
  - Why not "a state that takes another and changes parts": a state is shows, keys, conditions and timers; taking all of it would need a way to remove, where a set only adds. Not ruled out.
  - Not built: taking an object out of a set (`<hide>`).
- Open:
  - **Per-state object behavior.** Done 2026-10-15: states and scenes own objects, which run only while their state (and scene) is current, and `<show state>` draws a state still under another ([scenes](12-scenes.md)). Before, a state only chose which objects were *shown*; every shown object with a velocity moves, so the invaders cannot stand still behind the menu and march only in play. Ideas: a per-`<show>` override (`velocity="0"`); `<enter>`/`<exit>` commands; an `active` flag states switch; a freeze verb; separate copies per state (possible today, duplicates definitions). Related to where behavior belongs: state, object, or the pair. [Scenes](12-scenes.md) would need it (pause drawing a scene without running it).
  - **Passing data between states (settled 2026-10-15: looks).** Space Race, Combat and Freeway had two win screens that differed only in their words, and Air-Sea Battle three. What the transition has to carry is *which* outcome, and a look is exactly that: the end state owns one object with a look per outcome, and the condition that ends the game says `<become object="wins.winner" sprite="player2" />` before its `<push>`. No new language; a text's size is measured again when its look changes, so centring follows. Numbers go by path (`playing.rocket1.score`). Looked at and shelved: a condition handing the state it pushes the object that triggered it, as a reserved name (`trigger`, `winner`). It would be the one name in a file whose meaning changes while the game runs; printing "PLAYER 1" would need objects to carry words, which nothing gives them; and it saves one condition per player. High scores turned out not to be about states at all, but about a value surviving the reset and a copy made while running: see `<keeps>` below.
  - Settings screens exist as states but there is no settings vocabulary.


## Conditions

- Problem: a declarative file has no place to end a game at 15 points. The conclusion was that some conditional is unavoidable, so call it a **trigger**, not an `if`. It belongs in `playing`, not `paused`.
- **Built (state-level):** checked each frame while the state is current; the first match runs its commands and stops checking for the frame. Filter by `class` and/or `object`, then exactly one of:
  - `<atleast>N</atleast>` on a variable (reached it),
  - `<atmost>N</atmost>` (fallen to it: Frogger counts lives *down* with `<dec>` so the starting number lives in the frog's own `<variable>`; fires at or below because a variable can skip zero),
  - `<above>`, `<below>`, `<equal>` (more than, less than, the same; built 2026-10-14),
  - `<remaining>N</remaining>` (no more than N matching objects still in play, i.e. visible; hidden and dead objects do not count).
- **Comparing two variables (built 2026-10-14).** Any of the five variable tests takes, instead of a number, another variable: `<above object="gun2" variable="score" />`, read every frame. The attributes name what is compared with, as the condition's own `object` and `variable` name what is tested; without `object=` it is the tested object's own variable, so a `class` condition compares each object with itself (`<atleast variable="best" />`). Air-Sea Battle needed it for its winner: at time up `gun1`'s score `<above>` `gun2`'s, the reverse, or `<equal>`, each into its own end state. Chosen this way because the rule is "no data in strings": an operator in an attribute (`compare=">"`), an expression (`<atleast>gun2.score</atleast>` read every frame, which would also change what every existing threshold means), or a dotted `of="gun2.score"` were all strings to take apart. `<above>` and `<below>` are strict where `<atleast>`/`<atmost>` are not, since a tie is a third outcome with two variables; with whole counts and a number, `<atleast>N+1` already said "above". Names are words, like the tests before them: above/below/equal rather than greater/less/same. Checked at load: the object named exists and has the variable (with a suggestion), or every object the condition tests has its own; `<remaining>` takes only a number.
- A condition can run state commands plus `<inc>`, `<dec>`, `<become>`, `<reveal>`, `<play>`, `<silence>` and `<trigger>`; one that changes the variable it reads can count and start over (Frostbite turns four blue rows white and takes 4 off the count).
- Choices: a name that says what it counts rather than an operator or expression; `remaining` counts visible objects, not enabled ones (a text with collisions off is still there); a filter matching nothing warns at load because "none left" would be true at once; `<reset />` on the game-over screen restores variables so a leftover condition does not fire again.
- Not built: a comparison with an expression of variables (`gun2.score + 3`), object-level conditions (change color above a speed, a death animation at 0 health), states-as-predicates (no moves left, a timer), win/lose as first-class terms (compare VGDL's TerminationSet). A condition's numbers are load-time constants ([values-and-names](04-values-and-names.md)); a variable to compare with is not.
- **Condition sets (built 2026-10-13): `<conditions name>` beside `<keys>` and `<shows>`,** the same rule a third time. 25 conditions were written word for word in more than one state (Pitfall's way a screen ends ×4, Berserk's out of lives and extra man ×4, Megamania's out of lives and out of energy ×3, Demon Attack, Kaboom, Missile Command ×3). A state takes a set with `<condition set="name" />`, which has nothing else on it, and the reader (and the generator) put the set's conditions in its place. Order matters, since only the first condition that holds runs in a frame, so the set stands where its conditions stood; where a game's shared conditions were not next to each other (Berserk, Megamania) each became a set of its own rather than moving one. Six games went 13,497 lines to 13,436. The schema's condition test became optional so a `<condition set>` validates; a condition with neither is caught by the reader. No shipped game uses one since the rewrite on scenes (2026-10-15): what the places shared became the playing state's own conditions.
  - Looked at and left: writing the variable as one dotted name (`variable="status.lives"`, as `<inc>` does) instead of `object` plus `variable`; a `class` condition ("any paddle's score") cannot be written that way, so both spellings would stay.
- **Keeping a value between games, and copying one (built 2026-10-15): `<keeps>` and `<copy>`.** A best score needs two things a game could not say: a value that outlives `<reset />` (which put every object back), and a command that sets one variable to another's number as it is now (`<inc>`'s amount is worked out at load). `<keeps>`, after the game's `<objects>`, lists `<keep object="..." />`s that a full reset passes over entirely (variables, place, looks); `<reset object>` still resets one by name. `<copy variable="ship.score" into="best.score" />` names both as owner.variable, like `<inc>`, so nothing is read from an expression while running. Galaxian, which never ends, shows its best this way: a condition `<copy>`s the score into `best` while the score is `<above>` it. The author took `<keeps>` "for now", open to something more elegant later. Looked at: a flag on the object (`<kept>true</kept>`, like `<drawn>`), which reads well but scatters what survives a reset across the file; `<set variable="best.score">ship.score</set>` read live, which is the expression-read-while-running that comparing two variables turned down. Keeping across runs and entering initials were built next (below).
- **A table of the best, initials, and keeping on disk (built 2026-10-16).** Three small pieces, each general, rather than one high-score element. (1) **A text is its pieces**: `<content>`, `<number>` and the new `<letter>` in any order, a space between them and letters side by side one word, each `<number>` or `<letter>` that is owner.variable live. A letter is a number shown as one (0 is A, round again both ways), so initials are three variables that `<inc>`/`<dec>` already change and the display wraps, with no new arithmetic. (2) **A group's text that names the group's variable means each member's own** (`table.score` in the group `table`), the one place a group's name in a value means "this member"; it lets one sprite serve every row. (3) **`<rank variable="entry.score" into="table" />`**: the table is a group whose members, in the order written, are the places; the entry takes the first place it beats, with all its variables, and the rest move down. A tie stays below, as on the arcade machines. Whether a score makes the table is an ordinary condition (`<above object="table.5" variable="score" />`), so rank never needs to say. The initials are one state a letter (Galaxian's three), which the existing inputs say plainly; a cursor verb was looked at and not needed. **Keeping on disk**: the engine writes the kept objects (variables and look) to `saves/<game>.xml` in the games folder whenever a new game starts and when it closes, and reads it at start (`Engine::keepIn`, which xgecli, xgegui and a generated program call; tests do not, so they never see a saved table). Every game that keeps something lasts this way; nothing in the game file asks for it. The file is the engine's own XML, read a line at a time without an XML library, since a generated program has none. Looked at and set aside: a dedicated `<table>` element with columns (it would have to say how rows are drawn, which groups already do), variables holding text (a bigger change to the language than letters as numbers), and a file name in the game file (where saves go is the program's business). Open: a place's number (1. 2. 3.) needs a text per member today; columns of numbers do not line up in a proportional font.
- **Players taking turns (built 2026-10-16): swap the play.** The author chose, over writing each player's objects out twice and switching which set is in play, that each player has a whole game of their own and the engine swaps them, as the arcade boards swapped RAM: any one-player game becomes two-player with a few lines. A player's game is every object the game does not keep, every state's and scene's timers and the current scenes; kept objects (the best, the table) are everyone's. `<turns>` with a `<player>` each starts it, and the number of players is the number of `<player>`s, so there is no count to write. A `<player state=>` is pushed when that player's turn begins: per-player commands nested inside `<turns>` were looked at and set aside (commands inside a command, for one use), and a state does it with what states already do (its own words, a timer that pops). `<pass />` and `<out />` are the two ways a turn ends; when the turns are over `<out />` lets the rest of its list run and otherwise stops it, so `<out /><reset />` says "next player, or a new game" without a condition that can see how many are left. A turn is played in the state current at `<turns>`, and a pass takes off what is above it (a game-over screen, initials), so the next player always lands in play. Only a state's commands can swap, never a collision mid-frame. Open: showing every player's score at once (each score is in its own game), and a built-in for "whose turn" beyond the player's own state.
- **Attract mode (built 2026-10-16): recorded play.** The author chose a recording over a scripted computer player or a state drawn under the title. A game is the same every time from the same seed and the same keys on the same frames, so a `<demo>` is just that: a seed, a frame count and the key changes (`<press button>frame</press>`, `<release>`), after `<states>`. `<demo />`, a state command, plays it as a new game; a key at the window or the end of the recording stops it and starts a new game with what is kept as it was before (a demo never sets the best). `xgecli --record` writes it into the game file in place of the old one, by text so the rest of the file is untouched. Looked at and set aside: a scripted player (verbs for "steer at the nearest alien", a language of its own for one use); a state drawn under the title (a state shown still is frozen, so it would need a way to run under another, and still needs something to press keys); replaying object positions instead of keys (large, and breaks with any change to the game). Open: the mouse, pads and paddles are not recorded; game-level `<random>` variables are drawn at load and so do not follow the seed; a demo does not notice it was recorded with an older version of the game.
- **Richer conditions (built 2026-10-16): `<all>`/`<any>` of `<check>`s, `total=`, `distance=`.** The three things conditions could not say. (1) **And, or**: a condition holds `<all>` or `<any>`, each a list of `<check>`s, every check a test written exactly as a condition's (its own `class`/`object`/`variable`, then one test tag) but with no commands; they nest. A check per test, not several tests under one filter, because the tests of a real "and" are about different things (the hero near the dragon, and the dragon still asleep). Looked at and set aside: `and=`/`or=` attributes chaining named conditions (an order of evaluation hidden in names), several test tags in a row meaning "and" (no "or", and one filter for all), `<not>` (each test has its opposite already: atleast/below, atmost/above). (2) **Totals**: `total="count|sum|highest|lowest"` turns what is tested from each object's variable into one number over everything matched and in play; the five tests apply to it unchanged, so "at least three bullets in flight" or "the players' scores together" need nothing new. `<remaining>` stays, as `total="count"` with `<atmost>`, since every shipped game says it that way. An attribute, because it picks what is measured. (3) **Distance**: `distance="name"` measures each matched object to the nearest in play of that name or group (the same middle-to-middle as `<chase>`), so "near" is a `<below>`. A class is not taken there, matching `<chase>` and `<aim>`. Adventure's dragon uses all three ideas but totals: it sleeps until the hero is within 160 pixels and wakes once (an `<all>` of a distance and its own `awake` flag, the flag needed because a condition fires every frame it holds). Open: a total or distance as a value inside an expression (`<inc>` by the count); a condition that holds once until it stops holding, without a flag.
- Second-batch ideas: guarantee a solvable start or treat "no legal move" as a loss (unwinnable boards); rules that read how well the player is doing and change stats ([ideas](57-ideas.md)).
