# Generating a program with XSLT

**Status:** Built: `--generate windows-cpp` covers every game. Details of the target: [structure](41-generator-structure.md), [rules](42-generator-rules.md).

## Approach

**What we looked for.** The format was chosen partly so a game could be transformed ([file-format](02-file-format.md)): a way to turn a game file into a program that plays it with none of the engine in it, as a test of whether the description really is the game, and as the start of other targets (another language, another machine).

**What we looked at.**

| Option | Notes |
|---|---|
| G1. C++ in xgecli walks the loaded `Game` and prints code | Reuses the loader, but the generator is engine code: every target is more C++ in the program |
| G2. XSLT on the game file | The format's own tool; a target is a folder of stylesheets, not a rebuild. Needs an XSLT processor |
| G3. A separate generator program | Cleaner split, one more program to build; can come later if xgecli outgrows it |

Processors: libxslt (XSLT 1.0 with EXSLT, C, in vcpkg and every Linux distribution), Xalan-C++ (XSLT 1.0, matches Xerces but barely maintained), Saxon (XSLT 3.0, Java or a C build with a different licence for the full version).

**Chosen: G2 with libxslt, run by `xgecli --generate <target>`.** A target is named platform-language (`windows-cpp`); the backends are assumed (SFML 3 for now; a later option can pick them, since naming every window, sound and XML combination in the target would multiply). `-g` stays the game; the long form only, plus `-o` for the folder. One stylesheet writes several files with `exsl:document` (XSLT 1.0 has one result; 2.0's `xsl:result-document` is the same idea): `main.cpp` is the real output, `CMakeLists.txt` and `README.md` are small fixed texts with the game's name in them. A stylesheet cannot copy a binary file, so its own result is a manifest of what it wrote and of the assets to copy, and xgecli copies them. Choices inside the stylesheets:
- *Static, not interpreted.* The program is the game's rules written out as statements (`deflect(o_ball, o_paddle1, edgeOfFirst, (45.0f));`), not the engine plus the XML as data. Collision pairs, which rules apply to which pair, edge rules and key bindings are worked out by the stylesheet.
- *The verbs' C++ was kept as text* in a `runtime.xml` that mirrored the engine's verbs, sweep and synthesizer, so generated Pong played like the engine's; that is what made the first target too big, and it is gone (below). The plain target keeps small helpers in `functions.xml` instead.
- *Expression text is tokenised in XSLT 1.0* (no regular expressions): names become C++ variables (`window.width.center` → `v_window_width_center`), everything else is copied. That is enough because the expression syntax is C-like; it is also the weakest part, and the reason the tags exist.
- *Arithmetic comes out as a person would write it.* An `<equation>` or `<formula>` becomes one infix expression (`v_window_width_center - v_title_width / 2.0f`), an equation's steps written in where they are used, with brackets only where C++'s precedence needs them (`a - (b - c)`, `(a + b) * c`), and plain expression text keeps no brackets when it is one name or number. The first version wrote an equation as a lambda of its steps and every divide as `xge::divide()`, faithful but unreadable. The cost: a divisor of 0 gives infinity, as the expression text does, not the 0 the engine's `<divide>` gives.
- *Refuse, never guess.* Every tag the target does not know stops it with `windows-cpp cannot generate <x> yet` and where; xgecli removes a folder it made. A program that silently lacks a rule would be worse than none.

**Rejected.** XSLT 3.0 (Saxon): text processing would be easier, but the C library is the one that fits a C++ program with vcpkg dependencies. The engine as a library inside the generated program: that is the engine, not a generated game. One file per object or state: the C++ is shorter as one file and nobody edits it.

### A plain target: windows-cpp (windows-cpp-full removed)

**What we looked for.** The first target worked, but generated Pong was about 1,700 lines (790 of copied engine: object type, swept collision, verbs, synthesizer; 800 of per-object code) where Pong by hand on SFML 3 is about 100. The author wanted the program to read as if written by hand, with nothing of the engine in it, laid out as: the header block, includes (local, third party, standard), global and tunable variables, the objects, forward declarations, `main`, then the definitions; and the stylesheet shaped the same way (`generate-main` calling `generate-window` and `generate-game-loop`, which calls `generate-events`, `generate-update` and `generate-render`).

**What we looked at.** (a) Trimming the first target: its size comes from being faithful to the engine (the sweep, every verb's edge cases), so trimming means changing what it is. (b) A new target that starts from the smallest game and grows, refusing everything else, beside the old one. (c) Replacing the old one outright: loses full Pong until the new one catches up.

**Chosen: (b), then (c).** `windows-cpp` is the new, plain target. The first one was kept as `windows-cpp-full` for a while, then removed at the author's call: it carried too much of the engine. Its choices above (static rules, tokenised text, readable arithmetic, refuse never guess) carry over; its copied runtime does not. `games/pong_min.xml` (two paddles and a ball, no menu, score, text or sound) is the game it was grown on, and comes out at about 230 lines; all of `games/pong.xml` comes out at about 480, plus the modules; Space Race and Freeway, mostly groups, at about 870 and 980; Breakout at about 500; Depth Charge at about 630; Frogger at about 1080; Kaboom, Demon Attack and Megamania at about 1060, 570 and 1240; Asteroids, Combat and Lunar Lander at about 1330, 790 and 520; Frostbite and Air-Sea Battle at about 1170 and 1090; Donkey Kong and Pitfall! at about 690 and 1560. Choices:

- *Collision is the engine's.* (First it was simple: move, then test where it landed, told apart by the smaller overlap. That was replaced by the engine's own sweep, below.)

**The shared core** (changed 2026-10-11, at the author's ask). The aim began as the most stripped down program that plays a game, "with nothing of the engine in it", and the plain target was kept small by writing each verb's rules again in simpler form. Each of those copies could drift from the engine, and did (a Pong ball leaving a paddle a few pixels short, a wall bounce a frame early, a circle tested against a circle by its middles where the engine tests it against the other's box), and the check against the engine (below) found them one at a time. The author's call: it is all right for a generated game to be most of the engine minus the layer that lets the engine have several window, sound and XML libraries, and the right shape for that is **one set of plain files that both use**. A few files in `lib/` have nothing in them but the standard library, and are the one copy of what they do:

| File | What it is | Used by |
|---|---|---|
| `synth.h`, `synth.cpp` | notes made into samples | every audio backend; a generated game with sound |
| `collide.h`, `collide.cpp` | overlap, the sweep (boxes, circles, pixels through a callback), bounce and deflect velocities | `CollisionDetector` and `CommandExecutor`; a generated game with physics |
| `motion.h`, `motion.cpp` | sticking, wrapping, hops, jumps, landing, climbing, shots, aim, chase, leap, acceleration, flying a path | `CommandExecutor` and `Game`; a generated game with physics |
| `bitmap.h`, `bitmap.cpp`, `color.h`, `types.h` | the rasterizers and the pictures they draw | the window backends; a generated game that draws a picture itself |

The engine feeds these Objects (an `Object` is the abstraction: a name, its rules, its look, a window backend to draw it) and a generated game feeds them the numbers of an SFML shape (`physics.h`, `pictures.h` and `sound.h` are the adapters, each a thin wrapper over the engine's functions). A generated game is a small engine of its own with no middle layer, for now: the same arithmetic, with the rules and the order of a frame written out for that game. The generator copies the files with a `shared=` module in its manifest (`generate.xsl`, `generate.cpp`), and the data build puts them in `output/<config>/lib/` so that `xgecli` finds them wherever the data folder is. *Looked at, not chosen:* a library built once and linked (a generated game would need the engine's build and its dependencies, where today it needs SFML only); a copy kept in step by hand (it drifted). *Rule for these files:* nothing but the standard library, no engine header, and nothing a generated game's own names can meet (a local named `body` met a game's tunable `body` once). *Not shared:* the object model and the frame loop, which are written out for each game, in the engine's order (below). The engine moves every object a little at a time and finds the earliest touch anywhere first; a generated game moves each thing once (`move<Name>()`, with the edges looked at just before, as the engine looks at them before it moves what moves), and then every rule about a touch runs (`update<Name>()`), each touch worked out by sweeping both things from where each began the frame (`physics::begin`, `meeting`) to where it is. *What that gets, and what it does not:* one thing meeting two others in a frame takes them in the order of the rules, not the earliest first (Berserk's man at a door and a wall in one step is the one game that differs for it), and a touch tested for each pair once a frame (`touchesThisFrame`) is the engine's once-a-pair.

**Checking against the engine** (`tests/test_generated.cpp`, run as `xgetest "[generated]"`). *Looked for:* a way to know a generated game plays as the engine does without a person playing each. *Chosen:* the same game, the same keys and the same random seed run in both, and the pictures at the same frames compared. Both draw into a picture in memory, not a window (nothing flashes up, and with no sound, while 23 games are tried); a generated program does it only when built with `BUILD_TESTING` (`XGE_TRACE`), so what a person is given has no test code in it, and `include/trace.h` is a module in every program, plain forwarding functions without the flag. The generated code reads held keys through `trace::keyHeld` always, which is `sf::Keyboard::isKeyPressed` outside the trace, so one text of the program serves both. *Pictures first, then positions:* what is compared first is what a player sees, which needs nothing exported; but a picture cannot say which object is wrong, nor see one under another, so each side also writes where every shown object is (`stateNNNN.txt`: a name and two numbers) and the two are compared to 0.05 of a pixel. A failure is looked at as the two BMPs and the two lists (`stateNNNN.txt`, `stateNNNN.engine.txt`). *Why the tolerances:* the engine draws each object once into a texture and draws that, the program draws the SFML shape or text itself, so a text's edge differs by up to about 64 in a colour and a shape's edge by a pixel or two where it sits between pixels; a tolerance of 64, a pixel next to one of the same colour in the other picture not counting, and 100 pixels allowed passes those and still fails a thing moved, missing or in another colour (a ball a few pixels out is hundreds). *Random numbers:* the engine used to seed from the random device every time a game loaded, so `Game` now takes a fixed seed (`game_expr::seedRandom`) and the generated `randomBetween` takes one from `trace::seed`; both are `std::mt19937` with `uniform_real_distribution<float>`, so the same draws come out if both draw in the same order, which is a thing the generator now has to keep (a `<reveal>` that draws a start again where the engine does not would show as a difference). The engine used to work out every timer's `<random>` once at load to check it, which used up numbers the generated program did not, so the check now puts the generator back. A start drawn again (a `<reset />`) used to draw the velocity before the position, where a game draws the position first when it loads, so the first reset of an Astrosmash rock gave it another height than the program's; `Game::drawStartAgain` now draws in the load order, which is the one the program uses. Not chosen: one random number for every `<random>` (the middle), which would need no order but never serves a Pong ball to either side. *Where it lives:* the engine's half is in the library (`trace.cpp`) and the test, not in `xgecli`, which stays a program for playing and generating; the generated program's half is its own `--trace` options, which have to be in it. Building the 23 programs needs a compiler and takes minutes, so it is a script (`games-build-all.bat`) and the test is hidden (`[.generated]`) and skips a game that is not built: build everything for `xgetest`, run the scripts to generate and build, then `xgetest "[generated]"`; `games-run-all.bat` is those steps in order. *The play:* 2000 frames of one script of keys pressed and let go at random from a fixed seed (the first version played a few dozen frames of a handful of keys, which hid almost every difference: with a long random play 18 of 23 games differed, and fixing those found the engine's own faults, below). *Open:* one script of keys for every game, so a game whose keys are not W A S D, the arrows and Space is played less; the sounds played are compared as a list (frame and name, in `sounds.txt`), not what they sound like; only SFML 3 draws offscreen.

**Open.** A `<reveal>` draws a `<random>` start again where the engine does not. A rule about a class is one loop per group in it, so Space Race's rockets have nine; a person might keep the lanes in one vector, which would need the generator to see that the groups differ only in numbers. What the shared core does not hold (the order of a frame, which rule runs when, what a rule is) is still written twice and can drift; `xgetest "[generated]"` plays each generated game against the engine and compares pictures and sounds (below), which needs a compiler, so it is a script's step and not part of an ordinary test run. A pair is tested every frame, where the engine tests it only when one of the two moves: a rule about two things that both stand still runs in the program and not in the engine (Frostbite with its floes stopped). Built with GCC and Clang on Linux and with Visual Studio 2022 (MSVC 19.44, `/W4`, no warnings) on Windows; played by no agent. A sound that cannot be made (no audio device) is silent, as in the engine. Other targets (another backend, another language, an 8-bit machine) and how backends are named for them.
