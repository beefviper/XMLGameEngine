# Generating a program with XSLT

**Status:** Built: `--generate windows-cpp` covers every game; its physics, pictures and sounds are the engine's own code, and it plays a frame in the engine's order (below). Details of the target: [structure](41-generator-structure.md), [rules](42-generator-rules.md).

## Approach

**What we looked for.** The format was chosen partly so a game could be transformed ([file-format](02-file-format.md)): a way to turn a game file into a program that plays it with none of the engine in it, as a test of whether the description really is the game, and as the start of other targets (another language, another machine).

**What we looked at.**

| Option | Notes |
|---|---|
| G1. C++ in xgecli walks the loaded `Game` and prints code | Reuses the loader, but the generator is engine code: every target is more C++ in the program |
| G2. XSLT on the game file | The format's own tool; a target is a folder of stylesheets, not a rebuild. Needs an XSLT processor |
| G3. A separate generator program | Cleaner split, one more program to build; can come later if xgecli outgrows it |

Processors: libxslt (XSLT 1.0 with EXSLT, C, in vcpkg and every Linux distribution), Xalan-C++ (XSLT 1.0, matches Xerces but barely maintained), Saxon (XSLT 3.0, Java or a C build with a different licence for the full version).

**Chosen: G2 with libxslt, run by `xgecli --generate <target>`.** A target is named platform-language (`windows-cpp`); the backends are assumed (SFML 3 for now; a later option can pick them, since naming every window, sound and XML combination in the target would multiply). `-g` stays the game; the long form only, plus `-o` for the folder. One stylesheet writes several files with `exsl:document` (XSLT 1.0 has one result; 2.0's `xsl:result-document` is the same idea): `main.cpp` is the real output, `CMakeLists.txt` and `README.md` are small fixed texts with the game's name in them. A stylesheet cannot copy a binary file, so its own result is a manifest of what it wrote and of the assets to copy, and xgecli copies them. Choices inside the stylesheets:
- *Static, not interpreted.* The program is the game's rules written out as statements (`deflect(o_ball, o_paddle1, edgeOfFirst, (45.0f));`), not the engine plus the XML as data. Collision pairs, which rules apply to which pair, edge rules and key bindings are worked out by the stylesheet.
- *The verbs' C++ was kept as text* in a `runtime.xml` that mirrored the engine's verbs, sweep and synthesizer, so generated Pong played like the engine's; that is what made the first target too big, and it is gone (below). The plain target keeps small helpers in `functions.xml` instead.
- *Expression text is tokenised in XSLT 1.0* (no regular expressions): names become C++ variables (`window.width.center` → `v_window_width_center`), everything else is copied. That is enough because the expression syntax is C-like; it is also the weakest part, and the reason the tags exist.
- *Arithmetic comes out as a person would write it.* An `<equation>` or `<formula>` becomes one infix expression (`v_window_width_center - v_title_width / 2.0f`), an equation's steps written in where they are used, with brackets only where C++'s precedence needs them (`a - (b - c)`, `(a + b) * c`), and plain expression text keeps no brackets when it is one name or number. The first version wrote an equation as a lambda of its steps and every divide as `xge::divide()`, faithful but unreadable. The cost: a divisor of 0 gives infinity, as the expression text does, not the 0 the engine's `<divide>` gives.
- *Refuse, never guess.* Every tag the target does not know stops it with `windows-cpp cannot generate <x> yet` and where; xgecli removes a folder it made. A program that silently lacks a rule would be worse than none.

**Rejected.** XSLT 3.0 (Saxon): text processing would be easier, but the C library is the one that fits a C++ program with vcpkg dependencies. The engine as a library inside the generated program: that is the engine, not a generated game. One file per object or state: the C++ is shorter as one file and nobody edits it.

### A plain target: windows-cpp (windows-cpp-full removed)

**What we looked for.** The first target worked, but generated Pong was about 1,700 lines (790 of copied engine: object type, swept collision, verbs, synthesizer; 800 of per-object code) where Pong by hand on SFML 3 is about 100. The author wanted the program to read as if written by hand, with nothing of the engine in it, laid out as: the header block, includes (local, third party, standard), global and tunable variables, the objects, forward declarations, `main`, then the definitions; and the stylesheet shaped the same way (`generate-main` calling `generate-window` and `generate-game-loop`, which calls `generate-events`, `generate-update` and `generate-render`).

**What we looked at.** (a) Trimming the first target: its size comes from being faithful to the engine (the sweep, every verb's edge cases), so trimming means changing what it is. (b) A new target that starts from the smallest game and grows, refusing everything else, beside the old one. (c) Replacing the old one outright: loses full Pong until the new one catches up.

**Chosen: (b), then (c).** `windows-cpp` is the new, plain target. The first one was kept as `windows-cpp-full` for a while, then removed at the author's call: it carried too much of the engine. Its choices above (static rules, tokenised text, readable arithmetic, refuse never guess) carry over; its copied runtime does not. `games/pong_min.xml` (two paddles and a ball, no menu, score, text or sound) is the game it was grown on, and comes out at about 370 lines (230 before the frame was the engine's); all of `games/pong.xml` comes out at about 620, plus the modules; Space Race and Freeway, mostly groups, at about 1180 and 1280; Breakout at about 700; Depth Charge at about 830; Frogger at about 1400; Kaboom, Demon Attack and Megamania at about 1290, 750 and 1530; Asteroids, Combat and Lunar Lander at about 1720, 970 and 720; Frostbite and Air-Sea Battle at about 1450 and 1290; Donkey Kong and Pitfall! at about 850 and 1810. Choices:

- *Simple collision, not the engine's* (replaced, below). Move, then test where it landed; a touch was told apart by the smaller overlap. Kept at first because no generated game had needed the sweep; it made the generated games play differently, so the frame is now the engine's.

### The engine's own code in a generated game (2026-10-11)

**What we looked for.** The plain target's helpers had become copies of the engine: `physics.h` (bounce, deflect, wrap, land, climb, the shots, chase, paths), `pictures.h` (`rasterizeRows`, `rasterizeLines` and the turning, from `bitmap.cpp`) and `sound.h`/`sound.cpp` (the synthesizer). Copies drift: generated Pong tested two circles as circles where the engine tests a circle against a box, met the right edge a pixel later than the engine, and every fix to a verb had to be made twice. The author asked for the generated games to use the same code as the engine, in the same style, so they play the same; the only difference meant to stay is that a generated game is SFML alone, with none of the other backends.

**What we looked at.** (a) Keep the copies and test them against the engine. (b) Link the engine library into the program: that is the engine playing the XML, not a generated game, and brings exprtk, Xerces and every backend. (c) Move the arithmetic of touching and of the verbs out of `Object` into plain functions on boxes and velocities, call them from the engine, and copy those files unchanged into the program, beside the rules the generator writes.

**Chosen: (c).** `lib/include/geometry.h` and `lib/source/geometry.cpp` hold the touch tests (`boxesOverlap`, `circleOverlapsBox`, `shapesOverlap`, `sweepShapes`, the pixel walk), the window's edges (`pastWindowEdge`, `insideWindow`) and what the verbs do (`bounced`, `deflected`, `stickInside`, `wrapAround`, `landOn`, `climbLadder`, `chase`, `wayTo`, `shotAlong` and the other shots, `pathStep`); `CollisionDetector`, `CommandExecutor` and `Game` call them for `Object`s. `Edge`, `Direction` and `opposite()` moved to `types.h`, `wholeDegrees()` into `bitmap.h`, and a `<sound>` as written (`RawSound`) into `command.h`, so `geometry`, `bitmap` and `sound` include nothing else of the engine. A generated program copies the files it needs into `engine/` (`types.h`, `geometry`; `color.h`, `bitmap`; `sound`, `audio.h`, `audio_sfml`), byte for byte, and its build compiles them. `physics.h` stays, smaller: it turns an SFML shape, sprite or text into a `Box` and back. Pictures are `xge::rasterizeRows` and the rest, turned into an `sf::Image` by a two-line `imageOf`; sounds are `xge::SoundDesc`s handed to `xge::SFMLAudio`, played by name (`audio.play("wall")`), as the engine plays them. `functions.xml` keeps only what is the program's own (`randomBetween`, `sign`, `framesFor`, `imageOf`, `hertz`). The rules stay written out as statements about the game's own objects; the engine's data model (`Object`, commands) stays out.

### The engine's frame order (2026-10-11)

**What we looked for.** With the arithmetic shared, the generated games still ran a frame their own way: each thing moved, then its edge rules and touches were tested where it landed, one object's update at a time. The engine looks at the window's edges before anything moves and sweeps every pair through the frame in the order they meet (`Game::updateObjects`, `moveObjects`), so a fast ball met a paddle a frame later or not at all, a thing pushed into another was put back by a guess at the side, and which of two touches came first depended on the file order of the updates.

**What we looked at.** (a) Keep moving then testing, and put things back more carefully. (b) Write the engine's frame into each generated program as the stylesheet's own C++. (c) Move the engine's sweep of two things and its loop over a frame into `geometry.h` as templates (`xge::sweepThings`, `xge::playFrame`), have `CollisionDetector` and `Game::moveObjects` call them, and have the generated program call the same two with its own pairs, sweep and rules.

**Chosen: (c).** `playFrame` takes the frame's pairs and three functions: how to sweep a pair through what is left of the frame, how to move everything part of the way, and what a pair does when it touches; it finds the earliest touch, moves everything to it, runs the rules, and goes on, each pair once, as the engine always did. `sweepThings` is the engine's test of two things, shapes then pixels. The generated screen update now runs the engine's order: the keys, the animations, the timers, the paths, `accelerate<Name>()` (climbing, pull, drag), `edges<Name>()` for what is shown and moving, before it moves (every edge's rules, top, bottom, left, right, none cut short), `move<Screen>()` (hops and jumps, then the pairs that may touch, in the file's order, played by `physics::playFrame` with the generated `sweepPair`, `advance<Screen>` and `touch`), `stick<Name>()`, then the conditions. `touch` is one `switch` over the pairs the game has (`enum class Touch`), each running the first one's rules about the second, then the second's about the first, with the edge the sweep met, so `bounce`, `deflect` and `land` use the side that was touched rather than a guess. A key sets a velocity when it is pressed or let go (`physics::steer`), as the engine's key events do. The rules are still written out as statements about the game's own objects; nothing of `Object` or the command list comes in.

**Still different.** `<thrust>` and `<turn>` change the velocity when the key is read, not inside the engine's `applyAcceleration` (same frame, earlier in it). The members of one group do not touch each other (no game has a rule about its own group). An `unless=` test is shapes overlapping, not pixels. Key presses are found by comparing the keys held with last frame's, standing in for the engine's events, so a key pressed and let go within one frame is not seen. On a screen with nothing that moves, a jump's frames do not count down.

**Open.** A `<reveal>` draws a `<random>` start again where the engine does not. A rule about a class is one loop per group in it, so Space Race's rockets have nine; a person might keep the lanes in one vector, which would need the generator to see that the groups differ only in numbers. The generated rules are a second, simpler copy of the verbs and can drift from the engine; a test that plays a generated game against the engine frame by frame would catch it, but needs a compiler in the test. Built with GCC and Clang on Linux and with Visual Studio 2022 (MSVC 19.44, `/W4`, no warnings) on Windows; played by no agent. A sound that cannot be made (no audio device) is silent, as in the engine. Other targets (another backend, another language, an 8-bit machine) and how backends are named for them.
