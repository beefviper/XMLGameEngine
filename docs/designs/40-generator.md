# Generating a program

**Status:** Built: `--generate windows-cpp` covers every game. A hand-written prototype of a readable generated game on the engine's shared frame was tried and set aside ([Prototype](#prototype-the-game-as-decisions-on-the-engines-modules)). XSLT stylesheets write the game file out as the engine's own data, and the generated program plays it with the engine's own code on SFML; a test checks each game's data against what the engine reads, field by field, and plays it against its file, frame by frame.

## Approach

**What we looked for.** The format was chosen partly so a game could be transformed with XML's own tools ([file-format](02-file-format.md)): XSD to check it, XSLT to turn it into a program of its own, as a test of whether the description really is the game, and as the start of other targets. Later the author set what matters most: a generated game must play exactly as xgecli and xgegui play it, using the same code for the frame, physics, collisions, keys and sound, and differ only in having no XML to read and no choice of window and sound libraries (SFML only). And it stays XSLT that turns the game file into the program.

**What we looked at.**

| Option | Notes |
|---|---|
| G1. XSLT writes the rules out as C++ statements | Readable programs (`physics::bounce(ballVelocity, edge)`). Every verb, the frame order and the input handling written a second time, in the stylesheets. Built first (below), then replaced |
| G2. The program embeds the XML and links the whole engine | Plays the same by construction, but carries an XML library and the backend choosing: the engine with one game, not a program of its own, and no transform at all |
| G3. The engine's data written by C++, the engine's runtime copied in | xgecli reads the file with `readGame` and writes the `GameData` as C++. Plays the same by construction; no XSLT. Built on 2026-10-11 and replaced the same day, for that reason |
| G4. XSLT writes the engine's data, the engine's runtime copied in | The stylesheets read the game file and write the `GameData` the engine would read from it, as C++; the program builds `Game` from it and runs the engine's `Engine`. A second reader, in XSLT, kept honest by a test that compares its data with `readGame`'s for every game |
| G5. xgecli writes what it read as an intermediate XML, XSLT turns that into C++ | One reader; XSLT only templates a dump of C++ structures, which uses the tool without the point of it |

**Chosen: G4.** What the engine has for it (from G3): `GameData` (`game_data.h`), the game as written, which `game_xml` reads a file into (`readGame(file, backend)`) and `Game(GameData)` works out and runs, so nothing in `game.cpp` reads XML; Engine's constructor that picks libraries by name in `engine_backends.cpp`, so `engine.cpp` takes the `Window` and `Audio` it is handed; and `game_expr::fixRandomSeed`, so a test can load two copies of a game that draw the same random numbers.

How it runs: xgecli (`xge/cli/source/generate.cpp`) first loads the game as it would to play it, so a game the engine will not load (the schema, then the reader's own checks) is refused and the stylesheets never see a broken one; then runs `games/generators/windows-cpp/generate.xsl` with libxslt (EXSLT's `exsl:document` writes the files), and copies in what its result lists. The stylesheets:
- `data.xsl`: `source/<game>.cpp`. Each tag becomes the line of C++ that makes what `game_xml.cpp` makes of it: `object.sprite = sprite("circle", "", ...)`, `edge(object.rawCollisionData, "vertical", { verb("bounce") })`, `state.input["w"] = { verb("trigger", ...) }`. A `<group>` is written as it is in the file: what the group gives (a `Member`), a function for each `<member>`, `<row>`, `<column>` or `<cell>` that changes something, then a line per member or cell naming the parts that change it (`addCell(all, group, "aliens.1.2", { row1 }, ...)`; each a call of its own, since a Debug build gives every statement's temporaries their own stack slot and Breakout's bricks written inline overflowed a 1 MB stack); which rows and columns pick a cell is worked out by the stylesheet. The small functions those lines call (`sprite`, `change`, `edge`, `made`, `place`, `addCell`...) are `modules/game_parts.h`, copied in unchanged: where `game_xml.cpp`'s rules for combining what it read live in C++ (a sprite of the same shape changes only what it gives, an edge rule's guard, a cell's gaps).
- `program.xsl`: `source/main.cpp` (makes the `Game`, an `SFMLWindow` and an `SFMLAudio`, silence if there is no sound device, and calls `Engine::loop`), `CMakeLists.txt` (finds or fetches SFML 3, exprtk and lunasvg, compiles with the engine's own warnings), `README.md`.
- `engine.xml`: the engine's files the program compiles, copied from `xge/lib/` byte for byte into `engine/` (everything `Game` and `Engine` are made of, `game_expr` with exprtk, `svg` with lunasvg, `window_sfml` and `audio_sfml`; none of `game_xml`, `xml_*`, `xsd_lite`, the other backends or the factories). xgecli copies them from `xge/lib/` in the repository it was built from (`XGE_ENGINE_FOLDER`).
- `text.xsl`: trimming as `game_xml` trims, C++ string literals, camel-case names.

Why it plays the same: the data is checked, and after the data everything is the same code. `test_generated_games.cpp`: building `xgetest-generated` generates every game (`tests.cmake`) and compiles its data in (an ordinary build does neither); each game's data is compared with `readGame`'s, every field of every object, state, sound and path; then the two are played side by side for 900 frames with the same keys and random seed, comparing every object's place, velocity, look, heading, variables and whether it is in play, and the state, each frame.

**Rejected.** Writing the expressions as C++ (no exprtk in the program): the engine evaluates them at load and some again while playing (a timer's `<random>`, a position that waits for a text's size), so the program would evaluate them its own way and could differ. Merging a group's sprites in XSLT and writing each member out whole: the data comes out many times the size of the file, where written as parts it is about the file's size.

### The first target: rules as statements in XSLT (replaced 2026-10-11)

XSLT 1.0 stylesheets wrote each game as a program a person might write on SFML: tunables, objects as SFML shapes, a function per screen and per object, each rule an `if` (generated Pong about 480 lines). It was grown from `games/descriptions/pong_min.xml` to every game. Its verbs were first copies of the engine's; they were moved into the engine's `geometry.cpp` (shared by both), and the frame was rewritten in the engine's order with the sweep loop shared as `xge::playFrame`. Differences remained (thrust and turn applied as the key was read, a group's members never touching each other, `unless=` by shapes, key presses found by comparing frames), each a second copy of something the engine does. What it taught: a copy of the engine's behavior, however carefully kept, drifts; sharing arithmetic is not enough when the order, the input and the rules around it are written again. So the stylesheets now write only what the file says, and a test holds them to the engine's reading of it.

### Prototype: the game as decisions on the engine's modules

**Status:** Set aside (2026-10-15). The hand-written prototype (`games/prototypes/pong_min/`, its `pong_min_prototype` program and `test_prototype_pong.cpp`) was removed to keep the build to the engine, its programs and the generated games; it is in the history up to commit 7163ea2, to bring back when the generated code should read like a program written for the game. The shared frame it led to (`frame.cpp`, `verbs.cpp`, `FrameRules`) stays: the engine and every generated game run on it.

**What we looked for.** What the author had in mind from the start: a generated game that reads like a program written for that game, and plays exactly as the engine does because it calls the same code for the real work. The engine, an interpreter, works out from the file what to call; the generated game has it written down; both then call the same modules.

**Why G1 drifted and G3/G4 gave up readability.** Three layers were mixed in `game.cpp`: the work (the arithmetic, already shared in `geometry.cpp`), the order a frame runs in, and the dispatch (what the file says happens at an edge or a touch). `checkEdge`, `moveObjects` and `applyObjectCollision` each did all three, so G1 could share only the arithmetic and had to write the order a second time, which is where it drifted; G4 shares everything by making the game data again.

**What the prototype does.**
- `frame.h`: `playOneFrame(objects, window, rules)` is the order and the moving, moved out of `Game::updateObjects`, `applyClimbing`, `applyAcceleration`, `applyHops` and `moveObjects`. At each moment it asks a `FrameRules` what the game says: which objects are in play, the timers, the paths, a thruster's fuel, an object at an edge, whether a stick holds, whether a rule answers between two objects, what a touch does, the conditions. Whether two objects can touch at all (both colliding, neither in the air, not one lockstep block) is the frame's own.
- `verbs.h`: what a verb does to an `Object` (`bounce`, `deflect`, `stick`, `wrap`, `ride`, `die`, `stop`, `restart`, `holdMove`), moved out of `CommandExecutor`, which now only picks the verb and its target. `random.h` is the one random source, `circleSprite`/`rectangleSprite` (`command.h`) the shapes, `HeldKeys` (`keycode.h`) the keys, `drawFrame` (`window.h`) the picture.
- `Game` is the interpreter: it implements `FrameRules` by looking in the file and runs the commands it finds through `CommandExecutor`.
- `games/prototypes/pong_min/source/pong_min.cpp` is `pong_min.xml` written as that game's `FrameRules`: the objects made in file order, `atEdge` bouncing the ball off the top and bottom and serving again at the sides, `touched` deflecting it off a paddle, `key` holding a paddle's move. About 150 lines, no game data, and it is built (`pong_min_prototype`) from only the frame, verbs, geometry, collisions, object, pictures, random and SFML window files: no `game.cpp`, `game_expr` or exprtk, `CommandExecutor` or XML library.
- `xge/tests/test_prototype_pong.cpp` plays it beside the engine playing the file, ten seeds of 3600 frames with the paddles moving, both measured as a window would measure them, and compares every object every frame. They match; changing the deflect angle by one degree fails at frame 433.

**What it taught.** Expressions are the hard part. `ball.angle * pi / 180` written as C++ differed in the last bit from the engine on about a third of serves, because exprtk folds the constants first (`angle * (pi / 180)`); the prototype writes it the way exprtk works it out. A generator writing expressions as C++ has to follow exprtk's rewrites, or the program has to evaluate them with the engine's evaluator. Also the order of a random draw follows the engine's `std::map` of variables, so alphabetical, not the file's order.

**Open.** Writing it with XSLT (the rules are a direct transform of the tags, much like G1's, but now with nothing of the frame in them); state stacks, conditions, timers and paths as `FrameRules` answers; whether expressions become C++ or stay exprtk's; and whether `Engine`'s loop (keys, frame, sounds, picture) becomes shared too, as `HeldKeys` and `drawFrame` already are.

**Open.** `data.xsl` reads the file a second time: a new tag or field in `game_xml.cpp` needs the same in `data.xsl` (and perhaps `game_parts.h`), and the data test fails until it has it. Other targets (another backend, another language, an 8-bit machine) would need the engine's runtime in that language, which is a port, not a generator. Built with GCC and Clang on Linux; MSVC not yet tried with this target.
